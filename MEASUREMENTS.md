# Measurements

Generated by `scripts/measure.py`. DuckDB submodule at v2.0.0; upstream SaneQL at 58e4a81 (/tmp/saneql_upstream).

## Headline

- The dialect is 24 grammar rules and 753 lines of C++ (code lines), on top of DuckDB's SQL grammar, transformer and binder.
- SaneQL's own translator spends 267 code lines on its bison grammar and 692 on its lexer, but 1682 on semantic analysis plus 1021 on its algebra: the semantic layer is the bulk there too. Here that layer is DuckDB's binder, shared with SQL.
- DuckDB's SQL grammar is 1107 rules (1263 code lines) with 33480 code lines of transformer. The SaneQL dialect adds 2.2% to the rule count and 2.1% to the transformer, and reuses the rest.
- Across the 22 TPC-H queries, SaneQL text is 185 lines against 608 for SQL (9553 vs. 9696 characters): the two languages say the same thing in about the same number of characters, formatted differently.

## Reading the numbers

- "Code lines" exclude blank lines and comment-only lines; "Lines" are physical lines. SaneQL's upstream
  numbers are for the whole translator, including parts (algebra, SQL writer) that have no counterpart here
  because the dialect emits DuckDB's AST directly.
- DuckDB's generated trampolines are counted separately: they are produced from the grammar and
  `grammar_types.yml` by `scripts/parser/generate_transformer_trampoline.py`, so the hand-written transformer
  is the fairer comparison for authoring effort. Both are code the dialect reuses rather than writes.
- The per-query character counts show the two notations carry the same information; the line counts show the
  SaneQL examples are formatted one operator per line while the SQL is formatted one clause element per line.
  Neither is a measure of readability.
- Not measured: parse-time overhead and the optional LLM generation-accuracy experiment.
